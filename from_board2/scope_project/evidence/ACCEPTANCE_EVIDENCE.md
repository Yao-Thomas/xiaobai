## 阶段4 FPGA 运算下放

**已在 PL 实现**（`rtl/scope_dual_core.v`）：

| 功能 | 实现 |
|---|---|
| 帧统计 min/max | 流式，采集时同步算 |
| 饱和计数 | 贴 0 / 贴 1023 分别计数 |
| 累加和（均值） | 32 位累加器 |
| 迟滞边沿数 | 门限取自上一帧 min/max，避免二次扫描 |
| 首末边沿间隔 | 一次除法即得周期 |
| 列 min/max 包络 | 1008 列 x 20 位，双口 BRAM |
| 可配置窗口 | WIN_START / WIN_LEN + DDA 列号 |
| 结果双缓冲 | Bank 锁定 / ACK，未 ACK 不覆盖 |

**未单独实现 1024 级直方图/1%-99%分位** —— 原因：FPGA 包络路径上线后，
UI 不再读取原始帧、也不再逐帧建直方图，该需求被包络路径取代。
（原 Python 直方图正是"每帧重算"的性能元凶之一，见阶段1。）

**关键实现要点（都踩过坑）**：
- 列号用 **DDA 增量累加**，除法由 PS 算好下发 -> PL 里没有除法器
- 包络 BRAM 的读-改-写**拆成两拍流水** -> 否则 Vivado 无法推断 BRAM，
  整块 1008x20 退化成触发器（实测 +40,320 FF / +26,000 LUT，导致 place 失败）
- 跨时钟域（写 20 MHz / 读 100 MHz）用 `set_max_delay -datapath_only 12ns` 约束

**C 回退路径保留**：`fpga_env` 能力检测失败时自动走 C 逐点路径
（`accept_log` 已验证：旧 bit 上正确判定不可用并回退，不崩）

# 补充：第10轮 ARM CPU 真实实测（2026-10-10 19:26:22）

## 方法

`scope_v4_work/cpu_steady.py` —— 按阶段7 的**真实配比**跑 60 秒稳态循环，
采 `/proc/self/stat` 的 utime+stime 得真实单核占用。
（离屏：`scr.flush` 打桩不写 /dev/fb0，桌面不受影响；
  但热路径用的 `blit_raw` 直接写显存 mmap，这一项是真实的。）

## 过程中修掉的【测试脚本自身 bug】

第一版把波形档写死成 0.033 s，**没读应用里的 `WAVE_DT`** ——
应用实际配的是 0.040 s（25 FPS），脚本却按 30 FPS 跑，测出 44.2% 的虚高值。
改为读 `A.TOUCH_DT / A.WAVE_DT / A.TEXT_DT` 后才准。

## 结果

| 项目 | 数值 |
|---|---|
| 墙钟时间 | 60.0 秒 |
| 进程 CPU 时间 | 20.740 秒 |
| **单核占用** | **34.6 %** (目标 <35% -> **PASS**) |
| 折合双核占比 | **17.3 %** (目标 <25% -> **PASS**) |

分项（按应用真实配置）：

| 档位 | 次数 | 累计 | 单次 |
|---|---|---|---|
| touch (125 Hz) | 5714 | 868.3 ms | 0.152 ms |
| wave (25 FPS) | 1444 | 13146.1 ms | 9.104 ms |
| text (6.7 FPS) | 396 | 4616.7 ms | 11.658 ms |
| net (1 Hz) | 60 | 32.1 ms | 0.536 ms |

## 本轮另外两处关键优化

1. **draw_stat 重写为「预裁背景 + 逐格 blit」**
   实测教训：真实信号有噪声 -> vpp/频率每个文字档都在变 ->
   **整块内容键缓存永远命中不了**。而且每格都做 `_stat_bg.crop()`
   （对 1024x600 大图裁剪）+ 整行 to_raw/blit_raw，这一档要 22.6 ms。
   改为预裁每格背景（只做一次）+ 只重画并 blit 真正变化的格子：**22.6 -> 11.7 ms**。

2. **波形档按规范取低速端** `WAVE_DT 0.033 -> 0.040`（30 -> 25 FPS）
   `draw_wave` 是最大单项（含 880 KB 背景拷贝 + 880 KB 显存写），
   规范允许 25~30 FPS，取 25 FPS 后这一档从 27.5% 降到 21.9%。

3. **验证后回退的两次尝试**（写进证据，避免重复走弯路）：
   - 把 5/7 次 `flush` 合并成 1 次 -> **实测完全无效果**（flush 不是瓶颈）
   - 用 `ctypes.memmove` 逐行零拷贝 blit -> **反而更慢**（9.14 -> 9.98 ms，
     ctypes 每次调用开销大于 mmap 切片）

# 补充：过量程提示完整链路验证（2026-10-10 19:27:09）

不需要信号发生器 —— 用**合成饱和帧**走完整显示链路，并用**像素计数**作客观证据。

脚本：`scope_v4_work/check_overrange_ui.py`（离屏，flush 打桩，桌面不受影响）

## 结果

| 步骤 | 结果 |
|---|---|
| ① 造 2048 点贴 0 + 2048 点贴 1023（最长连续 256） | C 检测判定 **过量程=True** |
| ② `over` 置起后参数行告警色像素 | 0 -> **65** （画出「过量程」文字） |
| ③ 顶栏告警色像素 | 0 -> **5495** （顶栏出现过量程告警） |
| ④ 通道分离：只让 CH2 过量程 | CH1=**0**，CH2=**65** -> **不串通道** |
| ⑤ 恢复正常后 | CH1=0，CH2=0 -> **告警消失** |

## 顺带确认的一个设计行为

未【显示】的通道，其参数文字用暗灰色画（`cv if on else fc`）——
所以只开 CH1 时，CH2 的过量程不会用告警色抢眼。
这是设计意图（没显示的通道不需要抢眼），顶栏会给出总的过量程提示。
测试脚本第一版没打开 CH2 显示，因此误判为"串了"，已修正用例。
