# 项目长期约定（AI 协作者必读）

> 本文件是**跨会话的长期约束**，优先级高于单次对话里的临时偏好。
> 违反本文件的方案即使能跑通，也不算合格交付。

---

## 规则 1 ★ 复杂运算一律放 FPGA（PL），不要丢给 PS / Python

**判据**：只要满足下面任意一条，就必须在 PL 里用 RTL 实现，不许在 PS 侧用 C/Python 循环做：

- 与**每个采样点**或**每个像素**相关（逐点/逐像素运算）
- 与**采集速率**相关（20 MHz ADC、100 MHz FCLK、像素时钟）
- 需要在**帧内实时**完成（不能等一帧采完再慢慢算）
- 需要**并行**（多通道同时、多抽头同时、多 MAC 同时）
- 会随数据量线性变慢的循环

**已经这么做的先例**（沿用这个风格）：

| 位置 | 内容 |
|---|---|
| `rtl/scope_dual_core.v` | 抽取、双 bank 环形写、迟滞触发状态机、Bank 锁定/ACK |
| `rtl/scope_env.v` | 流式 min/max、迟滞边沿、多周期平均、列包络 BRAM（已写好，待接入） |
| `rtl/scope_dual_axi.v` | 测试波形发生器、诊断计数 |
| PL 内已有 | `lcd_out`（v_tc + v_frmbuf_rd + rgb2lcd）、`gpu_2d`、audio formatter |

**反例（不合格）**：把 4096 点逐列扫描放在 Python 里循环 → 实测 0 FPS；同样的循环放 C 里 → 17 FPS；放 PL 里 → 应为 60 FPS 量级。

**PS 侧只允许做**：寄存器读写、帧搬运、UI 绘制与触摸、参数换算（常数级运算）。

## 规则 2 ★ 为 int8 CNN 加速器预留资源，不许吃光

Zynq-7020（`xc7z020clg400-2`）总量与本设计当前占用（2026-10-10 实测，`out/utilization.rpt`）：

| 资源 | 已用 | 总量 | 占用 | **空闲** |
|---|---|---|---|---|
| Slice LUTs | 17,294 | 53,200 | 32.51% | 35,906 |
| Slice Registers | 25,740 | 106,400 | 24.19% | 80,660 |
| Block RAM Tile | 10 | 140 | 7.14% | **130** |
| DSP48E1 | 2 | 220 | 0.91% | **218** |
| Bonded IOB | 81 | 125 | 64.80% | 44 ← 唯一紧张 |
| BUFGCTRL | 9 | 32 | 28.13% | 23 |

时序：`All user specified timing constraints are met` ✓

### 预留给 int8 CNN 的额度（**硬上限，不许突破**）

| 资源 | 预留额度 | 说明 |
|---|---|---|
| **DSP48E1** | **≥ 64** | 够 64 路 int8 MAC，100 MHz 下 ≈ 6.4 GOPS |
| **Block RAM** | **≥ 40 块** | ≈ 1.4 Mbit，够 LeNet~小型 CNN 的权重+激活 |
| **Slice LUTs** | ≥ 10,000 | 控制/数据通路/量化/池化 |
| **Slice Registers** | ≥ 12,000 | 流水线寄存器 |

**即：示波器+外设那部分，LUT 不得超过 43,000、BRAM 不得超过 100、DSP 不得超过 156。**

### 每次改 PL 后的强制自检

1. 跑 `report_utilization`，确认仍满足上表
2. 若某项逼近上限 → **先优化现有逻辑（时分复用/资源复用），不许挪用 CNN 额度**
3. IOB 已用 64.8%，**再加外设引脚前必须先查管脚冲突**（LCD 占 J3，AD 模块占 J4）

## 规则 3 int8 CNN 的实现约束（预留接口，先想清楚再动手）

- **量化**：权重/激活均 int8（有符号），累加用 int32，最后再量化回 int8
- **接口**：以 AXI4-Stream 进激活、AXI4-Lite 配寄存器，或直接挂到 HP 口走 DDR
- **时钟域**：单独开一个 CNN 时钟（建议 100~150 MHz），不要和采样时钟/像素时钟混
- **不要**把 CNN 塞进 `scope_dual_*` 这套 IP 里 —— **另起一个独立 IP**，通过 AXI 互联
- **不要**为了省事用 PS 的 NEON/标量循环跑卷积 —— 违反规则 1

---

## 规则 4 其它已确认的硬约束（沿用）

- **J3（EXT_IO）整条被 LCD 占用** → 双通道 AD 模块必须插 **J4**（BANK13 + B34），且**反插 180°**（JP1 pin1 → J4 pin40 +5V）
- **时基表全系统只有一张**（`scope_processing.TIME_DIV`）—— 一旦出现两张，硬件 dec 和算频率用的 dt 就不一致（曾导致 25500% 误差）
- **配置变更走 `ScopeModel.commit()` 原子提交**，UI 不许直接写硬件寄存器
- **显示通道 / 当前调节通道 / 触发源** 三者必须独立，点"显示 CH2"不许改触发源
- **Bank 没 ACK 前 PL 绝不覆盖** → 宁可丢帧并累加 `lost_frames`，也不产生拼接帧
- 板子无外网，`apt` 不可用；只在板上编译 C（`gcc -O2 -fPIC -shared`）
- `.cmd` / `.ps1` 必须纯 ASCII；Python 里别打印 `✓`/`√`（板上 GBK 控制台会炸）

## 规则 6 ★ 部署 PS/UI 时**不要动操作系统或桌面服务**

**反复踩过的坑**：部署脚本先 `systemctl stop zynq-desktop` 再顶替桌面跑应用，
中途任一步失败就会留下「文件没换 + 桌面被停」的状态，用户看到的就是**旧版 UI**
（而文件哈希其实没变，极难排查）。

**正确做法**：
- 桌面每次点图标都是**重新启动应用** → **只要把文件替换掉就够了** ✓
- 用 `sudo cp /tmp/xxx /home/zynq/ui/` + `rm -rf __pycache__` ✓
- **不要** `systemctl stop/start zynq-desktop` ✓
- **不要** 改 `/etc/`、systemd unit、autostart ✓
- 换 bitstream 需要重启，属于必要动作，但**必须先备份旧 bit**并征得同意 ✓

**部署后必须校验哈希**：板端 `/home/zynq/ui/` 与本地 `ps/` 逐个 md5 对比 ✓

## 规则 7 ★ PL 改动前先跑"单模块快速综合"（30 秒）

整条构建 25 分钟，但**只综合 `scope_dual_core.v` 只要 30 秒**：

```tcl
read_verilog rtl/scope_dual_core.v
synth_design -top scope_dual_core -part xc7z020clg400-2 -mode out_of_context
report_utilization -file out/core_util.rpt
```

**任何 RTL 改动先跑这个**，确认语法 + 资源没爆，再启动完整构建 ✓
本次就是靠它定位到「包络同拍 RMW 导致 BRAM 退化成 40,320 个触发器」，
把核的 LUT 从 24,464 降到 2,839 ✓

**已知的 Vivado 陷阱（都踩过）**：
- 同一拍内读-改-写同一块存储器 → **无法推断 BRAM**，整块变触发器 → 必须拆两拍流水
- `x / y` 或 `x % y`（y 非常量）→ **综合出除法器** → 列号换算要用 DDA 增量累加
- 含异步复位的块里驱动多个 `output reg` → 可能报 `[Synth 8-91] ambiguous clock`
  → 改用同步复位
- `localparam [4:0] REG_x = 5'h20;` → **超出 5 位会截断** → 寄存器多的 IP 一开始就把地址位宽开够

## 规则 8 ★ UI 性能优化与"测量纪律"

### 8.1 先量再改，别猜

本次"还是很卡"的真凶**不是数据通路**（FPGA 下放后只要 0.5 ms/帧），
而是 **UI 绘制**（一帧全量重画 89 ms）。靠猜会白干。

**测量工具**（都在 `scope_v4_work/`）：
| 脚本 | 用途 |
|---|---|
| `breakdown_ui.py` | 逐函数测绘制耗时 |
| `measure_ui.py` | 离屏 + **触摸注入**，测响应/切换耗时 |
| `cpu_steady.py` | 按真实配比跑 60 秒，采 `/proc/self/stat` 得真实 CPU |
| `check_cache.py` | **验证缓存没把功能改坏** |
| `mem_sample.sh` | 长跑时采内存/线程/句柄，判断有无泄漏 |

**★ 离屏测量法**：正常构造 `Screen()`，然后把 `scr.flush` 打桩成空操作 ——
**一个字节都不写 /dev/fb0，桌面完全不受影响**，但仍能测出真实耗时
（热路径用的 `blit_raw` 是直接写显存 mmap 的，那部分仍是真实开销）。

**★ 触摸注入法**：`fbui.Touch` 内置支持写 `/tmp/ui_tap`：
```
"x,y"                        单次点击
"down:x,y" / "move:x,y" / "up:x,y"   单独注入（测长按）
"drag:x1,y1;x2,y2"           拖拽
```

### 8.2 五个实测有效的优化手法

1. **字形缓存** —— `fbui.text()` 画一个字符要 **1.1~1.3 ms**（CJK 字体本身就慢）。
   把单字渲染成小位图缓存，之后画字符串只是若干次 `paste`。
   数字 1.14 -> 0.53 ms/字，中文 1.29 -> 0.40 ms/字。
2. **内容键缓存** —— 把"显示内容"做成键，内容不变就只 `paste` 缓存图。
   `draw_top` 16.89 -> **0.51 ms**（33 倍），`draw_scales` 36.00 -> **5.07 ms**（7 倍）。
3. **逐项缓存**（不是整块）—— `draw_cards` 23.89 -> **1.00 ms**（24 倍），
   `draw_ctl` 20.56 -> **1.19 ms**（17 倍）。改一个字段时只有那一项重画。
4. **★ 缓存粒度要匹配"变化粒度"** —— 真实信号有噪声，
   `draw_stat` 的 vpp/频率**每个文字档都在变** -> 整块内容键缓存**永远命中不了**。
   必须降到**逐格缓存 + 预裁每格背景 + 只 blit 变化的格子**：22.6 -> **11.7 ms**。
5. **纯 Python 循环搬进 C** —— 触发电平虚线原来是双层 Python 循环（504 次迭代，4.5 ms），
   改调 C 的 `sd_hdash`：`draw_wave` 13.14 -> **8.25 ms**。

### 8.3 试过但**实测无效/更差**的（别再走弯路）

| 尝试 | 实测结果 |
|---|---|
| 把 5/7 次 `scr.flush()` 合并成 1 次 | **完全无效果** -> flush 不是瓶颈，文字才是 |
| `ctypes.memmove` 逐行零拷贝 blit | **反而更慢**（9.14 -> 9.98 ms）：ctypes 每次调用开销 > mmap 切片赋值 |
| `create_string_buffer(data)` 做源缓冲 | **更慢**（13.5 -> 23.1 ms）：每帧又多拷 1 MB |

### 8.4 ★★ 测量工具本身也要被验证

`cpu_steady.py` 第一版把波形档**写死成 0.033 s**，没读应用里的 `WAVE_DT`（实际 0.040），
于是按 30 FPS 跑，测出 **44.2% 的虚高值**。改成读 `A.TOUCH_DT / A.WAVE_DT / A.TEXT_DT` 后才准（**34.6%**）。

**同样地**：验证用例的前置条件没设全，会把**正确行为误判成 bug**。
例：测"CH2 过量程不串到 CH1"时没打开 CH2 显示 -> 未显示通道用暗灰色画文字（设计如此）
-> 误判"串了"。**下结论前先确认用例本身是对的。**

### 8.5 用像素比对做客观证据

验证 UI 显示（如过量程告警）不要靠肉眼：`count_color(img, box, rgb, tol)`
统计目标区域里告警色像素数。本次证据：参数行 0 -> **65**，顶栏 0 -> **5495**，
只让 CH2 过量程时 CH1=**0** / CH2=**65**（不串通道），恢复后归 0。
