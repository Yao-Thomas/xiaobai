# 板端可行性结论（模型① 量化）

> 任务 D 验收点之一：量化后能否在板端加载（或明确决定走云端）。
> 本文是**分析版**结论；服务器上运行 `quantize_llm.py` 后会生成带**实测数字**的
> `lora_model/quant/feasibility.md`（表内"实测回填位"）。

## 量化体积（分析值）

基座 Qwen2.5-0.5B-Instruct，参数约 0.49B：

| 精度 | 权重体积 | 备注 |
|---|---|---|
| bf16 | ≈ 980 MB | 原始权重 |
| INT8（weight-only per-channel 对称） | ≈ 490 MB + scale | `wq=round(w/scale)`，scale=max\|w\|/127 |
| INT4（group_size=128 对称） | **≈ 245 MB + scale ≈ 8 MB** | `wq=round(w/scale)`，scale=max\|w\|/7 |

> 任务书里写的"0.5B INT4 约 350 MB"是保守估计；按参数实际算权重只有 ~250 MB。
> 但**权重小不等于能跑**，见下。

## 板端内存账（1 GB RAM 硬约束）

```
板子总内存                                          1024 MB
系统基线（Ubuntu 20.04 桌面 + 音频服务 + agent + GPU 驱动）  ≈ 500~650 MB
────────────────────────────────────────────────────────────
可用余量                                            ≈ 350~500 MB
0.5B INT4 权重                                      ≈ 250 MB   ← 已吃掉大半
transformers 库 + Python 解释器                     ≈ 200~400 MB
KV cache + 激活 + tokenizer/embedding 高精度保留      ≈ 数十~数百 MB
────────────────────────────────────────────────────────────
⇒ 几乎必然 OOM；即使不 OOM，双核 Cortex-A9（无 NPU）首 token 延迟为秒~十秒级
```

## ★ 明确结论

**板端加载 0.5B INT4 在 1 GB RAM、且跑完整桌面的板子上不可行/不可靠。**

**决定：走云端，板子只做转发；本地离线降级用纯标准库 RAG（知识库 + 代码共几十 MB，秒级响应）。**

这是任务书明确允许的结论（"不行就纯走云端，板子只做转发"），并满足"明确决定"的验收要求。
