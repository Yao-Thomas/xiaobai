## 一、结论速览

| 项 | 结论 |
|---|---|
| **总体可行性** | ✅ 可行（他的设计明确保留了 LCD / 以太网 / PS I2C） |
| **最大冲突** | ❌❌ **音频 I2S 的 6 根引脚被他让出** ⇒ 我们的 ES8388 音频数据通路会废 |
| **次要冲突** | ❌ pl_led（2 根）、uart1（2 根） |
| **无冲突** | ✅ LCD（29 根）、以太网（14 根）、PS I2C（触摸 + ES8388 配置）、gpio0 |
| **地址冲突** | ⚠️ 他和我都用 `0x43CC0000`（他 SCPx / 我们 SCOP）⇒ 必须合并或二选一 |

## 二、版本差异（重要）

| 来源 | 魔数 @0x34 | 版本 |
|---|---|---|
| 他板子上的 bitstream（Oct 8） | `0x53435033` = "SCP3" | 较旧 |
| 他工程包寄存器表（Oct 10-11 导出） | `0x53435034` = "SCP4" | **最新** |
| 我们板子上的 bitstream | `0x53434F50` = "SCOP" | 我们的 scope_cap_axi |

**★ 核心设计原则（md 原话）：逐点/逐像素的运算一律放 PL，PS 只做寄存器读写、帧搬运、UI 绘制与常数级换算。**
- 反例：4096 点逐点扫描 → Python 0 FPS / C 17 FPS / PL 60 FPS 量级

## 四、★ 关键接口（AXI 寄存器表，阶段4）

基地址 `0x43CC0000`，字索引 `[11:2]`，字节偏移 = 字 × 4。

**控制类（PS 写）**
| 字节 | 寄存器 | 说明 |
|---|---|---|
| 0x00 | CTRL | bit0 翻转启动 / bit1 翻转停止 |
| 0x0C | DEC | 抽取倍率 |
| 0x14 | TRIGLEV | 触发电平 0..1023 |
| 0x18 | TRIGCFG | bit0 边沿 [2:1] 模式 [4:3] 触发源 |
| 0x1C | PRE | 预触发点数 |
| 0x54 | LOCK | bit0 锁定请求 / bit1 bank / bit2 应答 |
| 0x60 | HYS | 迟滞宽度 |
| 0x64 | ACQMODE | 0=Auto 1=Normal 2=Single 3=Roll |
| 0x7C | TESTPAT | 内部测试波形（方波/三角，2048 点 = 9.765kHz） |
| 0xA4 | WIN_START | 显示窗口起点 |
| 0xA8 | WIN_LEN | 显示窗口长度 |
| 0xAC | COL_STEP | 列号 DDA 步进 = round(1008×65536/win_len)，**PS 算好，PL 无除法器** |

**状态类（PS 读）**
| 字节 | 寄存器 | 说明 |
|---|---|---|
| 0x34 | VERSION | 魔数 SCP4 = 0x53435034 |
| 0x38 | CAPS | 能力位 |
| 0x3C | RATE | 采样率 20 MHz |
| 0x44/0x48 | DESC0/DESC1 | {bank, start_addr} / sample_count |
| 0x50 | LOST | 丢帧计数 |
| 0x58 | FLAGS | triggered / locked / busy |

**★ 阶段4 新增（性能关键）**
| 字节 | 寄存器 | 说明 |
|---|---|---|
| 0x10 | ENV_PTR | 写起始列（bit10=通道，bit9:0=列号） |
| 0x04 | ENV_DATA | 读该列 {max,min}，**硬件自动 +1**，到 1007 翻另一通道 |
| 0x80-0xA0 | ST_MM1/2, ST_SUM1/2, ST_CLIP1/2, ST_EDG1/2, ST_N | 帧统计（PL 流式算，PS 只读） |

**★ 包络路径的巨大改进：**
```
旧：写 RDPTR + 读 RDATA，每点 2 次事务，4096 点 = 8192 次
新：ENV_PTR=0 后连读 1008×2 = 2016 次单事务读
⇒ 这就是 CPU 从 95~100% 降到 34.6% 的关键
```

| 冲突 | 影响 | 严重度 |

| **音频 I2S 6 根** | zynq-audio / ES8388 数据通路失效 | ★★★ 高（语音功能基础） |

## 六、★ 他踩过的坑（必须吸取）

### 1. 改 PL 必须同步改设备树，否则内核 panic
```
现象：只把 .bit 写进 p1，重启 → 内核 panic 在 clk_wzrd_probe
      Unhandled fault: imprecise external abort (0x406) → 黑屏
原因：新 PL 删掉了 camera/HDMI/i2c2，但 dtb 还有这 9 个节点
      ⇒ 内核 probe 不存在的寄存器 ⇒ 总线 abort
解法：fdtput 把这 9 个节点标 status="disabled"
      /amba_pl/clk_wiz@43c80000        ← panic 就出在这
      /amba_pl/v_tc@43c90000
      /amba_pl/v_frmbuf_wr@43c40000
      /amba_pl/v_frmbuf_rd@43ca0000
      /amba_pl/i2c@41600000（及 ov5640@3c 子节点）
      /amba_pl/drm_pl_disp_hdmi
      /amba_pl/atk_hdmi_drm
      /amba_pl/vcap_dvp
★ 验证方法：先只装补丁设备树、保持老 PL 重启一次 —— 能正常启动说明补丁安全
```

### 2. 正确开发顺序
```
① 改 .v/BD → Vivado 综合实现 → .bit + .hwh
② ★ 同步更新设备树（.hwh 重生成，或 fdtput 打补丁）
③ ★ 先用 JTAG 烧 .bit 验证 PL 逻辑（不碰 SD 卡、不重启、随时换）
④ 确认 PL 没问题，才把【新 .bit + 新 dtb】一起写进 SD 卡
⑤ 写卡前先备份
```

### 3. 他写的救砖流程
```
u-boot autoboot 只有 3 秒 → 脚本每 150ms 敲回车打断
fatload mmc 0:1 0x00800000 <备份bit>; fpga loadb 0 ...
fatload mmc 0:1 0x00200000 zImage
fatload mmc 0:1 0x00100000 system.dtb
bootz 0x00200000 - 0x00100000
★ 纯 RAM 操作，不改卡
★ 救回来后先 systemctl stop zynq-screen-guard（否则黑屏看门狗会重启）
```

## 七、两个待解决问题（他自己文档承认的）

### 1. ★ 包络路径只填 95/1008 列（掉帧 + CPU 高的根因）
```
现象：PL 包络只填 95/1008 列，波形临时走 C 回退路径
定位：变 win_len(256~4096) 与 dec(1/2/3/6/12)，实测【恒定 95 列】、与两者无关
      ⇒ 固定比例 9.375% ⇒ 指向 in_win 门控 或 包络写地址位宽问题
修好后可去掉 C 回退，进一步降 CPU

★ 用户认为这与【缓存和亚稳态】有关
★ 他在 3.5 节用了 set_max_delay -datapath_only 12ns 放宽了包络 BRAM 的 CDC
  （写 20MHz / 读 100MHz），但没做真正的跨时钟域同步
  ⇒ 这可能就是"恒定 95 列"的病根
```

### 2. 其他
```
· 多点/查表标定（VPP_CAL 扩成多点，每通道独立，补直流电平标定）
· int8 CNN 接入（预留额度充足，独立 IP + 单独时钟 + AXI HP/DMA，不要塞进 scope_dual_*）
· 触发增强（脉宽/斜率/视频触发）
· 数学通道（CH1±CH2、FFT 应放 PL 或 C）
· 深存储（现在 4096 点，用 DDR + AXI HP 可做 M 级）
· 丢帧语义修正（顶栏"丢帧"是 PL 侧 Bank 未 ACK，不是 UI 丢帧）
```
