### 1.1 ★ 实测二：9 个节点的 status（板端 `/proc/device-tree` 直读）

| # | 节点 | reg | 板端 status 属性 | 结论 |
|---|---|---|---|---|
| 1 | `clk_wiz@43c80000` | `43 c8 00 00 00 01 00 00` | **无 status 属性** | **enabled** |
| 2 | `v_tc@43c90000` | `43 c9 00 00 00 01 00 00` | **无 status** | **enabled** |
| 3 | `v_frmbuf_wr@43c40000` | `43 c4 00 00 00 01 00 00` | **无 status** | **enabled** |
| 4 | `v_frmbuf_rd@43ca0000` | `43 ca 00 00 00 01 00 00` | **无 status** | **enabled** |
| 5 | `i2c@41600000` | `41 60 00 00 00 01 00 00` | **无 status** | **enabled** |
| 5b | `i2c@41600000/ov5640@3c` | — | `okay` | **enabled** |
| 6 | `drm_pl_disp_hdmi` | （无 reg） | **无 status** | **enabled** |
| 7 | `atk_hdmi_drm` | （无 reg） | `okay` | **enabled** |
| 8 | `vcap_dvp` | （无 reg） | `okay` | **enabled** |

> his `SCOPE_DUAL_DEPLOY.md` 里把这 9 个写成 7 条（把 `i2c@41600000` 和它的子节点 `ov5640@3c` 算成一条）—— 实际是 **9 个节点**：`clk_wiz@43c80000 / v_tc@43c90000 / v_frmbuf_wr@43c40000 / v_frmbuf_rd@43ca0000 / i2c@41600000 / ov5640@3c / drm_pl_disp_hdmi / atk_hdmi_drm / vcap_dvp`。

**★ 关键：其中 3 个（`ov5640@3c` / `atk_hdmi_drm` / `vcap_dvp`）已经有 `status = "okay"` 显式写着，其余 6 个连 status 属性都没有（DT 语义 = enabled）。** 这决定了补丁写法要分两种（改值 vs 插行），`make_dtb_patch.py` 两种都处理了。

### 1.2 ★ 实测三：我们 dtb 里**没有** scope / CNN 节点

```sh
$ find /proc/device-tree -maxdepth 3 -iname '*scope*'
（空）
$ grep -rl "43cc0000\|43CC0000" /proc/device-tree
（空）
$ grep -rl -i scope /proc/device-tree --include=compatible
（空）
```

同时 `/dev/mem` 裸读（只读，`PROT_READ`）：
```
0x43CC0034 = 0x53434F50   "SCOP"   我们的 scope_cap_axi
0x43CB0034 = 0x47505532   "GPU2"   我们的 gpu2d_axi
0x43CD0000 = 0x00000004            CNN IP 1
0x43CE0000 = 0x00000004            CNN IP 2
0x43C50000 = 0x01000000            audio_formatter
0x43C60000 = 0x00010000            i2s_receiver
```

**⇒ ★ 三个重要推论**
1. **`0x43CC0000` 的地址冲突和设备树完全无关**，它是**纯 PL 级**的地址分配冲突（两个 AXI-Lite 从机抢同一个槽）。所以：
   - **不需要**为了地址冲突改 DT；
   - 也不需要给示波器加 DT 节点（我们的 `scope_cap` 也没有，走 `/dev/mem`）。
2. 同理，**CNN 也不需要 DT 节点**。
3. ⇒ 设备树补丁**只管一件事**：新 PL 删掉的 IP，把对应的 DT 节点标 disabled。别的都不用动。

## 2. ★ 实测四：为什么必须「整组一起 disable」，不能只 disable `clk_wiz`

从我们 dtb 反编译出来的**实际引用关系**（phandle 实测）：

```
   phandle 0x08  =  clk_wiz@43c30000     (LCD 时钟)   ← 不能动
   phandle 0x20  =  v_frmbuf_rd@43c20000 (LCD fb 读)  ← 不能动
   phandle 0x21  =  v_tc@43c10000        (LCD 时序)   ← 不能动
   phandle 0x23  =  PWM@43c00000         (背光)       ← 不能动
   phandle 0x24  =  gpio@41200000        (LCD ID)     ← 不能动
   ─────────────────────────────────────────────────────────
   phandle 0x29  =  clk_wiz@43c80000     ★ HDMI 时钟
   phandle 0x27  =  v_tc@43c90000        ★ HDMI 时序
   phandle 0x26  =  v_frmbuf_rd@43ca0000 ★ HDMI fb 读
   phandle 0x2c  =  v_frmbuf_wr@43c40000 ★ 摄像头写
   phandle 0x2a  =  (i2c 总线给 DDC)
   phandle 0x2b  =  drm_pl_disp_hdmi/ports/port@0/endpoint
   phandle 0x28  =  atk_hdmi_drm/ports/port@0/endpoint
   phandle 0x2d  =  ov5640@3c/ports/port@0/endpoint
   phandle 0x1e  =  vcap_dvp/ports/port@0/endpoint
```

**HDMI / camera 组的依赖图**（从 dtb 原文读出）：

```
clk_wiz@43c80000 ──clocks(0x29)──► atk_hdmi_drm
v_tc@43c90000 ────xlnx,bridge(0x27)──► drm_pl_disp_hdmi
v_frmbuf_rd@43ca0000 ──dmas(0x26)──► drm_pl_disp_hdmi
drm_pl_disp_hdmi ◄──remote-endpoint──► atk_hdmi_drm
i2c@41600000 ──(总线)──► ov5640@3c ──remote-endpoint(0x2d/0x1e)──► vcap_dvp
v_frmbuf_wr@43c40000 ──dmas(0x2c)──► vcap_dvp
```

**⇒ 这是一个闭合的引用环，必须整组 9 个一起 disable。**
他当初只把 `.bit` 换掉、dtb 没动，内核去 probe **已经不存在的** `clk_wiz@43c80000` → `Unhandled fault: imprecise external abort (0x406)` → panic 在 `clk_wzrd_probe` → 黑屏。
**反过来也一样危险**：如果只 disable `clk_wiz@43c80000` 而留着 `atk_hdmi_drm`，后者会拿一个 disabled 的时钟 phandle 去 probe，同样出问题。

### 2.1 ★★ 好消息：LCD 链和 HDMI 链是**完全独立**的（实测确认，不是推测）

| LCD 链节点 | 它引用的是 | 有没有引用 HDMI 组 |
|---|---|---|
| `atk_lcd_drm` | `clocks = <0x08 0x00>`（= **clk_wiz@43c30000**） | ❌ 没引用 0x29 |
| `atk_lcd_drm` | `pwms = <0x23 ...>`（= PWM@43c00000） | — |
| `atk_lcd_drm` | `lcdID = <0x24 ...>`（= gpio@41200000） | — |
| `drm_pl_disp_lcd` | `xlnx,bridge = <0x21>`（= **v_tc@43c10000**） | ❌ 没引用 0x27 |
| `drm_pl_disp_lcd` | `dmas = <0x20 0x00>`（= **v_frmbuf_rd@43c20000**） | ❌ 没引用 0x26 |

**⇒ disable 那 9 个 HDMI/camera 节点，不会影响 LCD。**
`make_dtb_patch.py` 的**闸3** 就是自动验证这一条（13 个 LCD/音频/触摸节点必须仍在且 enabled）。

## 4. ★ 精确的补丁命令清单

### 4.1 实际可用的方法：dtc（★ 推荐，唯一可行的）

**为什么不用 fdtput**：
```
板上实测：which fdtput fdtget dtc devmem2   ->  全 MISSING
PC  实测：dtc / fdtput / fdtget / fdtdump   ->  全 MISSING（PATH 里）
但 PC 上 Vivado 自带：D:\Xilinx\2026.1\Vivado\bin\dtc.exe  (228,780 B)  实测可用
                     D:\Xilinx\2026.1\Vivado\bin\dtc      (406,184 B)
```
⇒ **不要走 fdtput 那条路。** 用下面三步（或直接用我写好的 `make_dtb_patch.py` 封装）。

**手工三步（等价于脚本内部做的事）**
```powershell
$DTC = "D:\Xilinx\2026.1\Vivado\bin\dtc.exe"

# ① 反编译（另存到 handover_b2\work\，不要在 _baseline 里改）
& $DTC -I dtb -O dts -o work\system.dts work\system_orig.dtb

# ② 在 work\system.dts 里这 9 个节点各加/改一行 status = "disabled";
#      · 已有 status 的：ov5640@3c / atk_hdmi_drm / vcap_dvp  —— 改值
#      · 没有 status 的：其余 6 个                          —— 在节点名下一行插入
#      ★ 一定要【从文件末尾往前改】，否则行号会错位（我第一版就踩了这个坑）

# ③ 编译回去
& $DTC -I dts -O dtb -o work\system_patched.dtb work\system.dts

# ④ 校验：★ 不要做二进制 diff！dtc 会重排 phandle / 规范化属性顺序，diff 会很大
& $DTC -I dtb -O dts -o work\verify.dts work\system_patched.dtb
#    然后【逐节点比对 status】+ 确认 bootargs 里还有 mem=992M
```

**一键版（推荐，带 5 道安全闸）**
```powershell
cd D:\ubuntu_iso
python handover_b2\make_dtb_patch.py handover_b2\work\system_orig.dtb handover_b2\work\system_patched.dtb --mode trim
# 或 --mode keep
```

### 4.2 fdtput 等价命令清单（**仅供参考/存档**，当前环境用不了）

> 记在这里是为了：万一以后给板子补上 `dtc`/`fdtput`（`apt install device-tree-compiler`，**但本次任务禁止在板上装东西**），或者别的同事有工具链时可以直接用。
> ★ 注意：`fdtput` 只**改已有属性**；对**没有 `status` 属性**的节点，`fdtput -t s ... status disabled` 在某些版本上会报错（属性不存在），得用 `fdtput -c`（create）。

```sh
# 目标：这 9 条（写成一行一条，便于复制）
fdtput -t s system.dtb /amba_pl/clk_wiz@43c80000        status disabled
fdtput -t s system.dtb /amba_pl/v_tc@43c90000           status disabled
fdtput -t s system.dtb /amba_pl/v_frmbuf_wr@43c40000    status disabled
fdtput -t s system.dtb /amba_pl/v_frmbuf_rd@43ca0000    status disabled
fdtput -t s system.dtb /amba_pl/i2c@41600000            status disabled
fdtput -t s system.dtb /amba_pl/i2c@41600000/ov5640@3c  status disabled
fdtput -t s system.dtb /amba_pl/drm_pl_disp_hdmi        status disabled
fdtput -t s system.dtb /amba_pl/atk_hdmi_drm            status disabled
fdtput -t s system.dtb /amba_pl/vcap_dvp                status disabled

# 校验（逐条读回，必须是 disabled）
for n in clk_wiz@43c80000 v_tc@43c90000 v_frmbuf_wr@43c40000 \
         v_frmbuf_rd@43ca0000 i2c@41600000 drm_pl_disp_hdmi \
         atk_hdmi_drm vcap_dvp; do
  echo "$n = $(fdtget -t s system.dtb /amba_pl/$n status 2>&1)"
done
echo "ov5640 = $(fdtget -t s system.dtb /amba_pl/i2c@41600000/ov5640@3c status)"

# ★ 必须同时确认 LCD 链没被误伤
for n in clk_wiz@43c30000 v_tc@43c10000 v_frmbuf_rd@43c20000 drm_pl_disp_lcd atk_lcd_drm; do
  echo "$n = $(fdtget -t s system.dtb /amba_pl/$n status 2>&1)"
done
echo "touch i2c = $(fdtget -t s system.dtb /amba/i2c@e0005000 status 2>&1)"
echo "bootargs = $(fdtget -t s system.dtb /chosen bootargs)"
```

> ★ **上面「校验」那一段的路径写对了一半**：我们板子上触摸和 ES8388 的 i2c 在 **`/amba/`** 下，**不在 `/amba_pl/` 下**：
> ```
> /amba/i2c@e0005000    ← i2c-2：0x14 Goodix 触摸 + 0x38 FT5426（读 LCD ID）
> /amba/i2c@e0004000    ← i2c-1：0x10/0x50/0x51 ES8388
> /amba/i2c@e0004000/es8388@10
> ```
> 而 `/amba_pl/i2c@41600000` 是 **PL 侧**的 i2c2（被 disable 的那个）。名字都叫 "i2c2"，**极容易搞错** —— 我第一次写脚本就把这条写成了 `/amba_pl/i2c@e0005000`，被安全闸 3 挡下来了。

## 5. ★★ 红线：`chosen/bootargs` 里的 `mem=992M`

我们 dtb 实测：
```
chosen {
    bootargs = "console=ttyPS0,115200 root=/dev/mmcblk0p2 rw rootwait mem=992M";
    stdout-path = "serial0:115200n8";
};
```

**`mem=992M` = 0x3E000000。** 而我们的 CNN 驱动里：
```python
/* cnn_linux.py:220 */
POOL_BASE = 0x3E000000        # DmaBuf 内存池基址
```
⇒ **992 MB 以上那 32 MB 是专门留给 CNN 的 `DmaBuf` 用的**（`cnn_linux.py:237-256` 用 `/dev/mem` 从 `POOL_BASE` 开始映射，不可缓存）。

**后果推演（必须避免）**：
- 若新 dtb 丢了 `mem=992M` ⇒ Linux 会用到 992M~1024M 这段内存 ⇒ CNN 的 `DmaBuf` 和 Linux 抢同一块物理内存 ⇒ **静默数据损坏 / 随机崩溃 / 文件系统损坏**。
- 而且这种错**不会**在启动时报错，只会在跑 CNN 时才发作 ⇒ 极难排查。

⇒ **已加硬闸**：`make_dtb_patch.py` 的**闸4** 会在编译后重新反编译输出 dtb，断言 `mem=992M` 仍在；不在就退出码 1、拒绝出产物。
（旁证：我们 `/mnt/boot/` 上有个 `system.dtb.bak_mem992`，说明这条 bootarg 是当初特意调过、保留下来的。）

**其他红线（脚本闸3 覆盖）**：LCD 链 5 个 + 背光 PWM + LCD ID gpio + 音频 3 个 + 触摸/ES8388 的 PS i2c，共 **13 个节点**必须仍在且 enabled。

```
前提：本次任务（分析阶段）不写板子。以下是【Lead 批准后的部署任务】才执行的步骤。

### 6.1 为什么必须先单独验证 dtb + 为什么 panic 会发生在 `clk_wzrd_probe`

- 内核按 DT 去 probe 节点。DT 里有的节点，**如果 PL 里没有对应寄存器，AXI 读会返回 abort**；PL 侧的 AXI 互连对未映射地址的访问会返回 `SLVERR/DECERR`，在 Zynq 上表现为 `imprecise external abort (0x406)`。
- `clk_wzrd_probe` 是**第一个**会去读 PL 寄存器的（clocking wizard 要读配置寄存器才能建时钟），所以 panic 出在它 —— **他踩的这个坑完全是 DT/PL 不同步，不是 PL 逻辑错**。
- 所以「先只换 dtb」这一步是**安全的**（老 PL 里硬件都在，disable 了只是不 probe），而「只换 .bit 不换 dtb」是**必炸的**。
