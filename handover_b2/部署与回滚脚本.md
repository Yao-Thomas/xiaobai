```

   ├─ /home/zynq/ui 五个基线文件 md5 必须全等基线
   ├─ /home/zynq/.scope_addr 是不是 0x43CC0000
   ├─ 10 个目标文件是否已存在（存在就拒绝覆盖，除非 --force）
   ├─ gcc / python3 / PIL 在不在；磁盘空间（实测 / 剩 25G，/mnt/boot 剩 181M）
   ├─ 本地 8 个源文件齐不齐 + 打印各自 md5
   └─ ★ 实测我们的 fbui.Screen 有没有 to_raw / blit_raw（他 apps 强依赖）

   ├─ cp -p 五个基线 UI 文件 + /home/zynq/.scope_addr

   └─ 写 manifest.json（含每个文件的 md5 + 期望基线值 + 新增文件白名单）
```

## 3. ★ 三个必须知道的坑（都是实测发现的）

### 3.1 ★★ 他的 `scope_dual.py` 和我们 `scope.py` 读**同一个标记文件**

```python
/* 他的 scope_dual.py:28-29 */
MARKER = "/home/zynq/.scope_addr"
DEFAULT_BASE = 0x43CC0000

/* 他的 scope_dual.py:77-81 —— 标记文件【优先于】DEFAULT_BASE */
if base is None:
    try:
        base = int(open(MARKER).read().strip(), 0)     # ★ 这里会覆盖 DEFAULT_BASE
    except Exception:
        base = None

/* 我们的 scope.py:19,68 —— 同一个文件！ */
MARKER = "/home/zynq/.scope_addr"
    base = int(open(MARKER).read().strip(), 0)
```

板端实测：
```
$ cat /home/zynq/.scope_addr
0x43CC0000
```

**⇒ 后果与错误做法**
| 做法 | 结果 |
|---|---|
| 只改 `DEFAULT_BASE` | ❌ 无效！`MARKER` 会把它顶掉，两个示波器还是读同一个地址 |
| 改 `/home/zynq/.scope_addr` | ❌❌ **灾难**：会把我们的单通道示波器一起搬到新地址 |
| ★ 给双通道用独立标记文件 | ✅ **正确** |

**`deploy_ps.py` 的做法**（局部补丁，只改 2 行）：
```python
# 补丁后
MARKER = "/home/zynq/.scope_dual_addr"      # ★ 独立文件，绝不碰 .scope_addr
DEFAULT_BASE = 0x43CF0000
```
并新增 `/home/zynq/.scope_dual_addr` 内容 `0x43CF0000`。
我们 `scope.py` 继续读 `.scope_addr = 0x43CC0000`（SCOP 不动）→ **两个示波器彻底解耦**。

实测补丁结果：
```
MARKER = "/home/zynq/.scope_dual_addr"
DEFAULT_BASE = 0x43CF0000
self.base = DEFAULT_BASE
OK: DEFAULT_BASE + MARKER 都改对了，旧 .scope_addr 已不残留
```

### 3.2 ★ 我们 `desktop.py` / `fbui.py` 是 **CRLF**，他的文件是 **LF**

实测（`_probe\test_encoding.py`）：
```
desktop.py   76088 bytes   BOM? False   CRLF count 1697   lone-CR 0
             decode utf-8 OK  chars=66947  re-encode==bytes? True
fbui.py      52590 bytes   BOM? False   CRLF count 1105   lone-CR 0
apps_scope_dual.py 48922 B  CRLF count 0        ← 他的文件是纯 LF
scope_dual.py      26506 B  CRLF count 0        ← 纯 LF
```

**⇒ 两个危险**
1. 若用 `open(p, "r", encoding="utf-8")` 读，Python 的**通用换行**会把 1697 个 CRLF 归一成 LF，写回去 ⇒ **一个 76 KB 的文件被无理由改动 1697 行**，diff 完全没法审、md5 也对不上基线。
2. 若再叠上 `errors="replace"`，万一文件不是 UTF-8（例如 GBK），中文会被**静默替换成 U+FFFD** —— 在部署场景里这是不可接受的。

**`deploy_ps.py` 的做法**：
```python
def read_text_exact(path):
    raw = open(path, "rb").read()
    try:
        txt = raw.decode("utf-8")            # ★ 严格解码，非法就报错（绝不用 replace）
    except UnicodeDecodeError as ex:
        raise Fail("不是合法 UTF-8 …… 拒绝静默损坏中文")
    crlf = raw.count(b"\r\n"); lf = raw.count(b"\n") - crlf
    return txt, ("\r\n" if crlf > lf else "\n")

def write_text_exact(path, txt):
    open(path, "wb").write(txt.encode("utf-8"))   # ★ 二进制写回，不做任何转换
```
并且**插入的行用原文的行尾**（`patch_desktop_text(txt, nl)`），所以 CRLF 文件补完还是 CRLF。
补丁里那个 `\{"name": "示波器".*?\},[ \t]*\r?$` 的 **`\r?` 必须有** —— CRLF 文本里 `$` 只匹配 `\n` 之前，不写 `\r?` 根本匹配不上这一行。（我第一版就是漏了这个。）

**实测（`_probe\test_transforms.py`）**：
```
编码=utf-8(严格)  行尾=CRLF  CRLF=1697  LF=0
原文件 76088 B  md5=7d25f5b0f2f3dcbf2b6d2f4786350027
补丁后 76897 B
强断言①：原文件每一行都原样在（只允许插入）
   原有 1697 行  ->  补丁后 1718 行；插入 21 行；原有行是否全在: True
强断言②：CRLF 行尾保持   CRLF: 1697 -> 1718
py_compile rc=0
L440: {"name": "示波器x2", "mod": "apps_scope_dual", "icon": icon_scope_dual, "tint": (235, 150, 60)},
L472: def icon_scope_dual(d, x, y, s):   (后面跟着 class Desktop -> 是)
幂等保护：重复打补丁被拒绝
ALL_TRANSFORM_TESTS_PASS
```

```

   ├─ 列出 /home/zynq/ui/_b2_backup_*（按时间排序，默认用最后一个）

   ├─ ★ 恢复前先校【备份里的】md5 == 基线值（防止备份本身是坏的）
   ├─ 若备份文件的 md5 不是基线 → 中止（备份不可信，别把文件搞丢）

   （已经是就不动；写后复读确认）

步骤 4  删除【白名单内】的新增文件（别的一律不删）
   ├─ 白名单 = deploy 新增的 10 个路径
   ├─ ★ 代码级断言：白名单与基线集合【绝不能有交集】，有交集直接抛错
   ├─ ★ 代码级断言：OUR_MARKER 绝不在白名单里
   └─ 顺手清掉这些模块的 __pycache__

步骤 5  最终校验
   ├─ 9 个基线文件 md5 必须全等基线
   ├─ 10 个新增文件必须全部不存在（--keep-new 时跳过这条）

步骤 6  写本地报告 _rollback_<TS>.json + 提示重启复核四项硬指标
```

## 7. 局限与待办（诚实说明）

| # | 局限 | 说明 / 处理 |
