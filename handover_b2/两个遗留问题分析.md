# 问题 1：PL 列包络只填 95/1008 列

## 1.1 现象（他自己文档里的原话）

   → 定位方法：变 win_len(256/512/1024/2048/4096) 与 dec(1/2/3/6/12)，
   实测恒定 95 列、与两者无关 → 固定比例 9.375% → 指向 in_win 门控或

```
`ps/apps_scope_dual.py:185-188`
```
# 原因：PL 的列包络写入有 bug —— 实测【恒定只有 95 列有数据】，
#   与 win_len(256/512/1024/2048/4096) 和 dec(1/2/3/6/12) 都无关，

**⇒ 关键信息：`恒定 95 列` + `与 win_len 无关` + `与 dec 无关` + `9.375%`。**

## 1.2 ★★ 根因：三个 bug 叠加，数字精确吻合到小数点后

### 结论先给

> **95 列不是"亚稳态"，也不是"缓存问题" —— 它是一个纯算术恒等式。**
>
> ```
> 每帧 write_sample 数 = 4096 + 1 + 2047 = 6144
> col_max = ⌊(6144 - 1) × 1008 / 65536⌋ = ⌊94.48⌋ = 94
> ⇒ 被写入的列 = 0..94 = 【95 列】        ← 与他实测「恒定 95 列」精确一致
> 比例 = 6144 / 65536 = 3/32 = 【9.375%】 ← 与他写的「固定比例 9.375%」精确一致
> ```

### 三个 bug，缺一不可

#### ★ BUG-A：`COL_STEP` 的 AXI 默认值写错了 16 倍

`rtl/scope_dual_axi.v:463-466`
```verilog
reg_win_start       <= 12'd0;
reg_win_len         <= 13'd4096;
reg_col_step        <= 24'd1008;      // COLS*65536/4096 = 1008      ← ★★ 注释和值都错了
cs_s1 <= 24'd1008; cs_s2 <= 24'd1008;
```

**正确值是 `1008 × 65536 / 4096 = 1008 × 16 = 16128`。作者漏乘了 16。**
验证一下他注释里的式子：`COLS*65536/4096` = `1008*65536/4096` = `1008*16` = **16128**，不是 1008。他把「`/4096` 相当于 `>>12`」和「`>>16`」搞混了。

对照 PS 侧的正确实现（`scope_dual.c:187-198`）：
```c
void sd_set_window(unsigned int start, unsigned int len) {
    ...
    step = (1008ULL * 65536ULL) / (unsigned long long)len;   // ★ PS 算的是对的
    sd_wr(R_COL_STEP, (unsigned int)(step & 0xFFFFFFu));
}
```
⇒ **只要 PS 调过 `sd_set_window()`，COL_STEP 就是对的。BUG-A 只有在 PS 从不调用它时才会暴露。**

#### ★★ BUG-B：PS **从来没调用过** `sd_set_window()`（这是让 BUG-A 暴露的直接原因）

`ps/apps_scope_dual.py:196-217`
```python
USE_FPGA_ENVELOPE = False                 # :196  ★★ 硬编码 False
self.fpga_env = False
if USE_FPGA_ENVELOPE and self.hw.hw:      # :198  永远不成立
    ...
self.m.commit(self.hw)
self.push_window()                        # :205

def push_window(self):                    # :207
    """把当前显示窗口告诉 PL（包络只在这段采样点上算）"""
    if not (self.fpga_env and self.hw.hw):
        return                            # :210  ★★ 直接 return，set_window 一次都没被调用
    span = max(16, min(DEPTH, self.m.tb.span))
    start = int(self.m.hpos * span / float(GRID_C))
    start = max(0, min(DEPTH - 16, start))
    try:
        self.hw.set_window(start, span)   # :215  这行从来没执行过
    except Exception:
        pass
```

**⇒ 全链路的实际执行情况**
```
USE_FPGA_ENVELOPE = False
  → self.fpga_env = False
    → push_window() 每次都在 :210 提前 return
      → sd_set_window() 从未被调用
        → R_WIN_START(0xA4) / R_WIN_LEN(0xA8) / R_COL_STEP(0xAC) 保持 AXI 里的默认值
          → col_step = 1008（错的）   win_start = 0   win_len = 4096
```

**⇒ 这直接解释了两个"无关"**

| 现象 | 解释 |
|---|---|
| **与 `win_len` 无关** | 作者以为自己在变 `win_len`（改 UI 的 Time/div 会改 `tb.span`），但 `push_window()` 提前 return ⇒ **PL 从来没收到过任何 win_len**，一直是默认的 4096。所以当然"无关"。 |
| **与 `dec` 无关** | 帧的结束是按 **write_sample 个数**判定的（`fill_count` 数的是"采了几个点"），不是按时钟数。`dec` 只改变"几个时钟采一个点"，**不改变一帧有几个 write_sample**。所以 `dec=1/2/3/6/12` 全一样。 |

#### ★ BUG-C：DDA 按【整帧】累加，而窗口只有 `win_len` 点；`col_acc` 只在 `start_pulse` 清零

`rtl/scope_dual_core.v:301-312`
```verilog
wire [ADDR_WIDTH:0] win_end = cfg_win_start + cfg_win_len;
wire in_win = (idx_rel >= {1'b0, cfg_win_start}) && (idx_rel < win_end);   // :302

reg [31:0] col_acc;
always @(posedge sample_clk) begin
    if (start_pulse) col_acc <= 32'd0;                                     // :309  ★ 只有这里清零
    else if (write_sample && in_win) col_acc <= col_acc + {8'd0, cfg_col_step};  // :310
end
wire [10:0] col_now1 = col_acc[26:16];   // 恒 < 1008                      // :312  ★ 注释说"恒 <1008"，其实不然
```

- `col_acc` 在每个"**在窗口内**的 write_sample"上加一次 `cfg_col_step`。
- 设计意图：窗口里恰好有 `win_len` 个点 ⇒ 累加 `win_len × (1008×65536/win_len) = 1008×65536` ⇒ `col_acc[26:16]` 走到 1007。**数学上是对的。**
- **但前提是「帧长恰好等于 `win_len`」。** 实际不是：
  - `win_start = 0, win_len = 4096 = DEPTH` ⇒ `in_win` **恒为真**（`idx_rel ∈ [0,4096)` 永真）。
  - 而**帧长是 6144 个 write_sample**（见下一节推导），不是 4096。
  - ⇒ 累加 6144 次，`col_acc` 冲到 `6144 × col_step`，远超设计值。
- **而且 `col_acc` 只在 `start_pulse` 清零**。AUTO 模式的"自动重新武装"（`core.v:504-513`）只重置 `write_ptr / fill_count / dec_count`，**不重置 `col_acc`**：
  ```verilog
  if (auto_rearm || roll_mode) begin
      busy <= 1'b1; triggered <= 1'b0;
      write_ptr <= {ADDR_WIDTH{1'b0}};
      fill_count <= {(ADDR_WIDTH+1){1'b0}};
      dec_count <= 16'd0;
      prev_s1 <= 10'd0; prev_s2 <= 10'd0; previous_valid <= 1'b0;
      // ★★ 没有 col_acc <= 0 !
  end else begin busy <= 1'b0; end
  ```

#### BUG-D：`env_col_d` 是 11 位，写进 1008 深的 BRAM ⇒ 越界写被丢掉

```verilog
(* ram_style = "block" *) reg [19:0] env1_mem [0:COLS-1];   // COLS = 1008
reg [10:0] env_col_d;                                       // ★ 11 位，能到 2047
...
env1_mem[env_col_d] <= { env_a1_d, env_a1_d };              // 越界时 Vivado 丢弃
```
`col_now1 = col_acc[26:16]` 是 **11 位（0..2047）**，而存储器只有 1008 个位置。一旦 `col_acc` 超过 `1008×65536`，列号就落到 1008..2047 ⇒ **越界写被综合工具丢掉**（Vivado 会报 index out of range 警告），读回来还是 0。
（1008 只需要 10 位：1007 = 0x3EF。用 11 位是唯一合理的写法——因为要顺带用 bit10 当通道选择——但写入时没有做范围保护。）

### 1.2.1 帧长 = 6144 的逐步推导（这是 95 这个数字的来源）

```
rtl/scope_dual_axi.v:474   reg_pretrigger          <= 12'd2048;   ← 默认预触发 2048
ps/scope_model.py          pre = int(pretrigger * 4096) = 2048    ← PS 侧也是 2048，两边一致

rtl/scope_dual_core.v:156-157
   wire [ADDR_WIDTH:0] post_count = DEPTH_COUNT - pretrigger_clamped - 1'b1;
                                  = 4096 - 2048 - 1 = 2047

rtl/scope_dual_core.v:170-171
   wire auto_timeout = ((cfg_trigger_mode == 2'd0) || no_trigger) &&
                       (fill_count >= DEPTH_COUNT);      // Auto 模式：填满 4096 就收帧
rtl/scope_dual_core.v:479-480
   if (fill_count < DEPTH_COUNT) fill_count <= fill_count + 1'b1;   // 到 4096 就停
rtl/scope_dual_core.v:486-487
   if (!triggered) begin
       if (frame_done_en && ((edge_hit && enough_history) || auto_timeout)) begin
```

逐步数 write_sample（`start_pulse` 后 `fill_count = 0`）：

| 第几个 write_sample | 该拍看到的 `fill_count` | 发生什么 |
|---|---|---|
| 1 .. 4096 | 0 .. 4095 | 只采样，`auto_timeout` 还是假（需要 `fill_count >= 4096`） |
| **4097** | **4096** | ★ `auto_timeout` 成立 ⇒ `triggered <= 1`，`post_remaining <= 2047` |
| 4098 .. 6144 | — | `post_remaining` 从 2047 递减；`post_remaining <= 1` 时 `done <= 1`，共 **2047** 拍 |

```
一帧 write_sample 总数 = 4096 + 1 + 2047 = 6144
```

**为什么是 `auto_timeout` 而不是真实触发？**
`edge_hit && enough_history` 只要信号越过迟滞门限就会提前收帧（`enough_history = fill_count >= pretrigger = 2048`），那样帧长会变。**实测能稳定复现"恒定 95"，说明测试时 `auto_timeout` 每一次都赢** —— 也就是**没有真实边沿触发**（ADC 输入是直流/未接模块，或不越过 `TRIGLEV`）。
坐实这一点的旁证：他自己 `SCOPE_DUAL_DEPLOY.md:18` 写「采集实测：CH1=893 / CH2=495（**未接信号时的稳定直流**）」——正是"没有边沿"的工况。
`auto_timeout` 是**确定性**的 ⇒ 帧长恒定 6144 ⇒ **列数恒定 95**。这也解释了为什么是"恒定"而不是"抖动"。

### 1.2.2 算出 95 和 9.375%

```
col_step = 1008（BUG-A 的错默认值）
col_acc 在第 k 个 write_sample 之前 = (k-1) × 1008
写入时用的列号 = col_acc[26:16] = ⌊(k-1) × 1008 / 65536⌋

最后一个 write_sample（k = 6144）：
    col_max = ⌊6143 × 1008 / 65536⌋ = ⌊6192144 / 65536⌋ = ⌊94.48⌋ = 94
⇒ 被写入的列 = 0,1,2,...,94  ⇒ 【95 列】
⇒ 列 95..1007 从未被写入（列号永远到不了 95）  ⇒ 与他"列 95~1007 从未被写入"精确一致

比例：6144 / 65536 = 0.09375 = 3/32 = 【9.375%】
⇒ 与他写的"固定比例 9.375%（= 96/1024）"精确一致
   （96/1024 = 3/32 同样精确；955/1008 = 9.4246% 也落在同一档）
```

**⇒ 三处独立数字（95 列 / 9.375% / 与 win_len 和 dec 无关）全部被同一组公式一次性解释。**

## 1.3 ★ 对「缓存 / 亚稳态」假设的评估：**不成立**

> 用户怀疑："和缓存 / 亚稳态有关"；"他用了 `set_max_delay -datapath_only 12ns` 放宽了包络 BRAM 的 CDC（写 20MHz / 读 100MHz），但没做真正的跨时钟域同步"。

**四条定量/结构性的反驳：**

1. **亚稳态不可能产生"恒定"的比例。** 亚稳态/CDC 失效的表现是**概率性、随机性**的：某些列偶尔取到旧值或错值，**列数会抖动**。而实测是「恒定 95 列」、跨 5 种 `win_len` × 5 种 `dec` = 25 组工况**完全不变**。这是**确定性算术**的特征，不是随机现象的特征。
   ⇒ **判据**：如果真是 CDC，重跑 100 次，列数应当有分布；实测是常数。

2. **9.375% = 3/32 = 6144/65536 是一个精确的有理数。** 亚稳态不会产生"精确 3/32"这样的数字。
   `6144 = 4096+2048` 正好是「DEPTH + 预触发默认值」——**只有纯算术路径才能解释为什么这个比例恰好等于帧长/2¹⁶**。

3. **`set_max_delay -datapath_only` 根本没有用在数据路径上，而是用在"读口地址"上，而地址是同域的。** 看 RTL：
   ```verilog
   always @(posedge rd_clk) begin                              // core.v:284-287  读口
       env_rd_data <= env_rd_col[10] ? env2_mem[env_rd_col[9:0]]
                                     : env1_mem[env_rd_col[9:0]];
   end
   ```
   - `env_rd_col` 来自 AXI 域（100 MHz `s_axi_aclk`），**读口也在 `rd_clk`（同一个 100 MHz）**。
   - 写口全在 `sample_clk`（20 MHz）。
   - 所以真正跨域的是 **BRAM 的写侧 vs 读侧**，而 BRAM 的读写口本身就是**物理上独立的双口存储器**，跨口读取"写同一地址"时硬件保证读到旧值或新值（都是完整的一个 20 位字）——**不会读出半个字**。因为 `{max,min}` 是在**同一个 20 MHz 时钟沿一次写入**的，是原子的。
   - ⇒ 最坏情况只是"某一列读到上一帧的旧值"，**不可能让列号停止增长**。
   - 他注释里自己说的「数据整帧不变，属合法 CDC」在**单次写入原子性**这点上是对的；`-datapath_only` 只是不让工具去分析这条组合路径的建立/保持，**并不会造成 95 列**。

4. **病根位置和 CDC 无关。** 95 这个数字完全由 `col_step = 1008`（BUG-A）和帧长 6144（BUG-C 的前提）决定，**都在写口地址生成逻辑里，与读口、与跨域无关**。

### 1.3.1 但 `set_max_delay -datapath_only 12ns` **仍然是一个真实隐患**（只是不是这个 bug 的病根）

`CNN_RESOURCE_BUDGET.md:47-48` / 他文档里写的：
```
4. 跨时钟域约束：包络 BRAM 写口 20MHz / 读口 100MHz，用
   set_max_delay -datapath_only 12ns 约束（数据整帧不变，属合法 CDC）。
```
**问题**：
- `set_max_delay -datapath_only` **只约束组合路径延迟**，它**不会**告诉工具"这里不需要时序分析"，也**不提供**任何同步器语义。它不产生任何电路。
- 这在"数据在传输期间保持不变（quasi-static）"的场景是**可以接受的工程手段**；但**必须同时**在 RTL 里保证"数据在被采样期间确实不变"。
- 现在的 RTL **没有任何"数据稳定窗口"的保证**：写口每 20 MHz 写一次，读口每 100 MHz 读一次，两者相位任意。**没有互斥、没有握手、没有 double-buffer。**
- ⇒ 后果：**某次读可能读到正在被更新的那一列**，波形上表现为**偶发的单列错值/毛刺**（而不是系统性错误）。
- `12ns` 这个数字也值得质疑：**20 MHz = 50ns 周期，100 MHz = 10ns 周期**。约束 12ns 比读时钟周期还长，等于放弃了对该路径的时序要求（这也是作者的本意），但因此**工具不会报任何 CDC 警告，问题被永久隐藏**。
- ⇒ **建议**：改成标准做法 —— `(* ASYNC_REG = "TRUE" *)` + 两级同步（如果是控制信号），或对 BRAM 读口加一个 `env_bank_ready` 握手/双缓冲（如果是数据）。**并加 `set_clock_groups -asynchronous`** 明确声明两个时钟域异步，让工具去查真正的 CDC 违规。

⇒ **结论：CDC 是一个需要修的独立隐患（会造成偶发单列错值），但它不是"恒定 95 列"的原因。两件事要分开处理。**

## 1.4 ★ 修复方案（按性价比排序 + 最小改动）

| # | 改哪里 | 改成什么 | 影响 | 必须吗 |
|---|---|---|---|---|
| **F1** | `rtl/scope_dual_axi.v:465,466` | `24'd1008` → **`24'd16128`**，并把注释改成正确式子 | 立即从 95 列 → **1008 列**（见 1.5 的判据 P2） | ★★ **必须**（一行） |
| **F2** | `rtl/scope_dual_core.v:312` | `col_acc[26:16]` 加**上界钳位**：<br>`wire [10:0] col_now1 = (col_acc[26:16] > 11'd1007) ? 11'd1007 : col_acc[26:16];` | 彻底堵住越界写（BUG-D），任何工况都不会写坏邻居 | ★★ **必须** |
| **F3** | `rtl/scope_dual_core.v:308-311` | 每次**进入窗口**就重置 DDA，而不是只在 `start_pulse`：<br>`else if (write_sample && in_win) col_acc <= (idx_rel == {1'b0,cfg_win_start}) ? {8'd0,cfg_col_step} : col_acc + {8'd0,cfg_col_step};` | 修掉 BUG-C：帧长 > `win_len` 时不再溢出，且短窗口也能填满 | ★★ **必须**（否则只有 `win_len=DEPTH` 时对） |
| **F4** | `rtl/scope_dual_core.v:504-513 与 536-544` | 自动重新武装时补一句 `col_acc <= 32'd0;` | 消除跨帧残留 | ★ 建议 |
| **F5** | `rtl/scope_dual_axi.v:462-468` | 上电默认值改为 `reg_col_step <= 24'd16128; win_ln <= 13'd4096;` | 让"PS 没下发"时也有合理默认 | ★ 建议（F1 已覆盖） |
| **F6** | `ps/apps_scope_dual.py:196` | `USE_FPGA_ENVELOPE = True` | ⚠️ **必须在 F1~F4 改完并重新出流之后**才改；否则只是换个姿势错 | ★★ **配套必须**，但顺序不能反 |

**★ 只改 F1 就够不够？** 只改 F1 时：`win_len=4096=DEPTH`、帧长 6144 ⇒ 前 4096 个 write_sample 把列推到 1007，后 2048 个 write_sample 的列号 ≥1008 ⇒ **越界被丢** ⇒ **看起来 1008 列全填满了** ✓。
但 `win_len < DEPTH`（如 256）时：`in_win` 只在每 4096 点里为真 256 次，一帧 6144 点里约 384 次 ⇒ `col_acc` 只到 384×258048 ≈ 1.5×1008×65536 ⇒ 越界 ⇒ 又丢。**所以 F1+F3 必须一起改。**

| **证据** | `ui_breakdown_final.txt:17-21`：`crop 0.35 + to_raw 1.88 + blit_raw 0.45 + paste 0.85 = 3.53 ms`，但 `draw_stat` 总耗时 **6.28 ms** ⇒ 差 **2.75 ms** |

### 2.5.1 CPU 优化优先级（按"改动量 / 收益"排）

| 优先级 | 做什么 | 预计收益（单核%） | 风险 | 验证 |
|---|---|---|---|---|
| **P-1** | ★ **修 `ui_perf_final.txt` 那个 100 倍错误**（先别优化，先把数字算对） | 0（但是**认知上的最大收益**） | 无 | P9 |
| **P-2** | `draw_wave` 的 `blit_raw` 改一次性 `memmove`（缓存 ctypes 视图） | **-9 ~ -10%** | 低（纯拷贝路径） | P10, P11 |
| **P-3** | `draw_scales` 去掉 anchor ⇒ 走字形缓存 | **-2.4%** | 低 | P14, P15 |
| **P-4** | `draw_stat` 加"值未变则跳过重绘" | -2 ~ -3% | 低 | P18 |
| **P-5** | 修 PL 包络（F1~F4）⇒ `step` 走 PL 路径 | **-1.2%**（★ 主要是为了波形正确） | 中（要重新出流） | P8 |
| P-6 | `TOUCH_DT` 0.008 → 0.010/0.012 | -1 ~ -2% | 低（触摸延迟仍 <60ms 目标） | P13 |
| P-7 | CDC 修正（F8） | 0（是正确性，不是性能） | 中 | P5, P6, P7 |

**⇒ 结论：真正能"降 CPU"的是 P-2 / P-3 / P-4（绘制层），合计约 14~15 个百分点（34.6% → 约 20%）。修 PL 包络（P-5）只值 1.2%，它的价值在正确性。**

## 2.6 一句话给 Lead

> **「CPU 高」主要是个数字错误：`ui_perf_final.txt:21` 把"每秒工作量 340.6 ms"标成了"每 100 ms"，于是 34.06% 被写成 3405.5%（100 倍）。他 60 秒真实实测是 34.6% 单核（`ACCEPTANCE_EVIDENCE.md:274`，进程 CPU 时间 20.740 s），已经达标。**
> 真正的 CPU 去处：`draw_wave` 21.9% + 文字档 7.7% + `step`(125Hz) ~7% + touch 1.4%。**85% 以上在绘制**，所以：① 先修测量脚本；② 优化 `blit_raw`（memmove，-10%）与 `draw_scales`（去 anchor 走字形缓存，-2.4%）；③ **不要指望修 PL 包络来降 CPU（只值 1.2%）**，那是修正确性。
