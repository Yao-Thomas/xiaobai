### 0.1 交接包目录结构（`板端部署.sh` 按这个约定找文件）

把 `板端部署.sh` 和下面这些目录放在**同一个目录**里，整包拷到新板子后执行：

```
交接包/
├── 板端部署.sh              ← 在新板子上 sudo bash 板端部署.sh
├── board_ui/                ← → /home/zynq/ui/        （§1 里所有 /home/zynq/ui/*）
├── board_agent/             ← → /home/zynq/agent/     （§1 里所有 /home/zynq/agent/*，含 kb/）
├── board_root/              ← → /home/zynq/           （§1/§2 里 /home/zynq/*.py、*.sh、*.json、*.bin、*.dtb、*.ko）
├── board_units/             ← → /etc/systemd/system/  （§4.2 的 13 个 unit + drop-in，需保持子目录结构）
├── board_etc/               ← → /etc/                 （zynq-baidu.env 等；★ 需接手人填自己的密钥）
├── board_bin/               ← → /usr/local/bin/       （gpu-load.sh）
├── board_lib/               ← → /lib/firmware/        （gpu.bin、cnn.bin）
└── board_boot/              ← → /mnt/boot/            （BOOT.BIN、boot.scr、zImage、system.bit、system.dtb、board_config.gz）
```

`board_units/` 内部保持 `zynq-agent.service.d/live-kb.conf` 这样的相对路径，脚本会原样还原。
`board_etc/` 里**不要**放 `/var/log`、对话文件、`.ssh` 等（见 §8）。

#### 4.2.1 `/etc/systemd/system/zynq-desktop.service`

```ini
[Unit]
Description=Zynq Framebuffer Desktop
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/zynq/ui
ExecStartPre=/bin/sleep 5
ExecStartPre=/bin/sh -c 'echo 0 > /sys/class/graphics/fbcon/cursor_blink 2>/dev/null || true'
ExecStartPre=/bin/sh -c 'echo "1 4 1 7" > /proc/sys/kernel/printk || true'
ExecStart=/usr/bin/python3 -u /home/zynq/ui/desktop.py
Restart=on-failure
RestartSec=6
StandardOutput=append:/var/log/zynq-desktop.log
StandardError=append:/var/log/zynq-desktop.log

# ★ 桌面卡死时它是收不到 SIGTERM 的（进程陷在内核里），systemd 默认要等 90s
#   才 SIGKILL，看门狗重启一次要一分半。压到 8s。
TimeoutStopSec=8
SendSIGKILL=yes

[Install]
WantedBy=multi-user.target
```

```ini

#
# ★★★ 2026-10-03 加：让 agent 以 root 跑
#
# 为什么
# ────────────────────────────────────────────────────────────────
# 用户报的问题链：跑 hw_verify 一直报「硬检查失败」——
#     [硬] ✗ scope_0 在线      读不到（期望 0x53434F50）
#     [硬] ✗ gpu_0 在线        读不到（期望 0xDEADBEEF）
#     [硬] ✗ CNN @0x43CD0000   SIGBUS
# 看着像 PL 里没有这些 IP，其实硬件完全正常：
#     root 身份读 0x43CB0034 -> 0xDEADBEEF  ✓
#     zynq 身份读同一地址    -> SIGBUS       ✗
#
# 根因：agent 原来是 User=zynq，但它的硬件工具全都要 root：
#     · /dev/mem   是 root:kmem 0640  → 读 PL 寄存器
#     · /dev/i2c-1 是 root:i2c  0660  → ES8388 读写
#     · mount /dev/mmcblk0p1 /mnt/boot → 刷 bitstream 必需
#     · cp 到 /mnt/boot                → 同上
#     · systemctl reboot               → 刷完重启
# 而 hw_tools.py 里本来就写着 _need_root_hint()：
#     "（提示：这个操作要 root，Agent 服务以 root 跑才行；
#       看 zynq-agent.service 的 User=）"
#   ⇒ 说明【原设计就是 root】，User=zynq 是后来改的，改漏了。
#
# 安全上怎么想
# ────────────────────────────────────────────────────────────────
# 有人可能担心"agent 拿 root 太危险"。但这块板子上：
#   · zynq 用户本来就在 sudo 组，而且 sudo -n 免密可用
#     ⇒ 即使不改 root，"能免密提权"这个事实也没变，安全性没有实质差别
#   · agent 真正的安全防线是三层【应用层】机制，不是 Unix 权限：
#       ① policy 门禁：22 条 confirm 规则，动硬件前要用户点「同意」
#       ② 变更单：谁在什么时候改了什么，全部留痕
#       ③ 一键回滚 + 硬件回归清单（hw_verify）
#   ⇒ 把权限卡在这里，只会让工具静默失败（就像刚才 hw_verify 那样），
#     反而看不出问题。
#
# 附带做了两件降低依赖的事（在代码里，不在这里）：
#   · agent/hw_change.py 的 read_pl 和 i2cget 现在会先探测权限，
#     不够就自动走 sudo -n —— 所以哪天这个 drop-in 被去掉，也不会退回到

Group=root
```

```ini
#   Playback(DAC数字) = 192 -> 0.00 dB   (量程 0-192)
#   Output 1/2        = 33  -> +4.50 dB  (量程 0-33)
```

```
thermal-cooldown (oneshot, Before=zynq-desktop)  ─┐
zynq-gpu-loader  (oneshot, Before=zynq-desktop)  ─┴─> zynq-desktop ──> zynq-screen-guard

      └─ ExecStartPre: audio_cap_init.py  (修 ES8388 0x0A = 0x00，麦克风才活)

thermal-guard (root)             DefaultDependencies=no，谁挂了它都得活着
```

几个**踩过的坑**（原注释里写得很清楚，交接时别改回去）：

- `cloud-api` **不能** `After=zynq-agent.service` + `Wants=network-online.target`：实测会导致开机根本不尝试启动（`journalctl -b -u cloud-api` 显示 `No entries`）。现在只依赖 `basic.target`。
- `zynq-agent` 必须是 **root**：`/dev/mem`(0640 root:kmem)、`/dev/i2c-1`(0660 root:i2c)、`mount /mnt/boot`、`systemctl reboot` 全都要 root。`User=zynq` 会让 `hw_verify` 报「硬检查失败」的**假故障**（读 PL 寄存器 SIGBUS）。
- `zynq-audio` 的 `ExecStart` **被 `alsa.conf` drop-in 覆盖**成 `audio_alsa_svc.py`。改 unit 主文件里的 `audio_svc.py` 是没用的（空 `ExecStart=` 之后才生效）。
- `volume-max.conf` 里 `i2cget/i2cset` 必须**写绝对路径**（systemd 的 PATH 没有 `/usr/sbin`），且那行 `ExecStartPre` 要加 `+` 前缀才会以 root 执行。
- `zynq-desktop` 的 `TimeoutStopSec=8`：桌面卡死时收不到 SIGTERM（进程陷在内核里），默认 90s 会让看门狗重启一次要一分半。

| `/lib/firmware/gpu.bin` | 4045532 | `zynq-gpu-loader.service` 通过 `fpga_manager` 加载的**字节交换** bitstream（GPU IP）|
| `/lib/firmware/cnn.bin` | 4045532 | CNN IP 用的 bitstream |
| `/lib/firmware/gpu.bin.bak_20261002_214625` | 4045532 | 备份，可不带 |

★ **`.bit` 不能直接给 `fpga_manager`**：Zynq 的 `fpga_manager` 要的是字节序翻转后的 `.bin`。
板上有转换脚本 `/home/zynq/bit2bin.py`，用法在 §2 表里。

★ **实测 `zynq-gpu-loader.service` 是 `disabled` + `inactive`**（见 §4）。
也就是说 `/lib/firmware/gpu.bin` 现在**不是**开机自动加载的 —— 实际由 agent 的硬件工具
（`hw_tools.py` 刷 bitstream 流程）或手工写入 `/sys/class/fpga_manager/fpga0/firmware` 完成。
因此「`/home/zynq/.gpu_addr` 标记存在」才是桌面走硬件加速的前提；
部署脚本只装 unit 并 `enable`，是否 `start` 由接手人决定。

`gpu-load.sh` 的完整逻辑（`/usr/local/bin/gpu-load.sh`，1364 字节）：

```bash
#!/bin/bash
# 开机自动加载 FPGA GPU bitstream
# 注意: PL 是易失的, 每次开机都要重新加载; 探测失败必须删标记,
#       否则桌面访问未解码地址会 SIGBUS 崩溃循环
BIN=/lib/firmware/gpu.bin
MARK=/home/zynq/.gpu_addr
BASE=0x43CB0000

log() { echo "[gpu-load] $*"; }

if [ ! -f "$BIN" ]; then
    log "没有 $BIN, 跳过 (桌面用软件渲染)"
    rm -f "$MARK"
    exit 0
fi

log "加载 $BIN ..."
if ! echo gpu.bin > /sys/class/fpga_manager/fpga0/firmware 2>/dev/null; then
    log "写入 firmware 失败, 跳过"
    rm -f "$MARK"
    exit 0
fi
sleep 2

ST=$(cat /sys/class/fpga_manager/fpga0/state 2>/dev/null)
log "FPGA Manager 状态: $ST"
if [ "$ST" != "operating" ]; then
    log "加载失败, 删标记"
    rm -f "$MARK"
    exit 0
fi

# 探测 (放在子进程里: 万一地址未解码触发 SIGBUS, 只死子进程)
if python3 - <<'PYEOF'
import sys
sys.path.insert(0, "/home/zynq/ui")
try:
    from gpu import GPU
    g = GPU(0x43CB0000, verbose=False)
    ok = g.probe()
    g.close()
    sys.exit(0 if ok else 1)
except Exception:
    sys.exit(1)
PYEOF
then
    echo "0x43CB0000" > "$MARK"
    chown zynq:zynq "$MARK" 2>/dev/null
    log "✅ GPU 存在, 已写标记 (桌面将使用硬件加速)"
else
    rm -f "$MARK"
    log "⚠️ GPU 无响应, 已删标记 (桌面回退软件渲染)"
fi
exit 0
```

> 设计要点：**探测失败必须删掉 `/home/zynq/.gpu_addr` 标记**，否则桌面会去访问未解码的 PL 地址直接 SIGBUS 崩溃循环。
> 探测放在**子进程**里跑，SIGBUS 只死子进程。这两点在新板子上必须保留。

### 7.3 ES8388 音频 codec —— 寄存器实测快照

codec 挂在 **I2C-1，从地址 0x10**，声卡为 `card 0: xlnxi2ssndcard0`，
runtime 驱动模块 `snd_soc_es8388`（`lsmod` 实测已加载）。

上电稳定后的寄存器快照（`es8388_regs_A.txt` / `_B.txt` 两次读数**完全一致**，说明已稳定）：

```
00: 06 50 00 09 3c 00 00 7c 00 66 50 02 00 0c 30 20
10: 00 00 c0 b0 32 06 00 00 03 22 00 00 08 1c 1f f7
20: fd ff 1f f7 fd ff 00 f8 28 28 f8 80 00 00 1b 1b
30: 1b 1b 00 aa aa 00 08 00 00 00 00 40 86 86 00 00
40: 06 50 00 09 3c 00 00 7c 00 66 50 02 00 0c 30 20
```

**关键寄存器（交接时必须知道的三条）**：

| 寄存器 | 值 | 含义 / 为什么关键 |
|---|---|---|
| `0x0A` | `0x00` | ADC 输入选择。★ 内核驱动默认写 `0x50`（LIN2/RIN2 = LINE_IN 插孔），但板上麦克风接在 **LIN1/RIN1**，必须是 `0x00`。实测 `0x50` 时采集只有 -93 dBFS 峰值 889（几乎静音），`0x00` 时 -66 ~ -75 dBFS 正常。**这就是 `audio_cap_init.py` 存在的唯一理由。** |
| `0x1D` | `0xF7`→bit1 置 1 | Vpp_scale。置 1 表示 4.0V 满量程（默认 0 = 3.5V，+1.16 dB）|
| `0x10` / `0x11` | `0x00` | ADC 数字音量（0 = 0 dB，量程 0-192）|
| `0x2E`/`0x2F` | `0x1B` | DAC 数字音量（`amixer sset Playback 192` 写到这）|
| `0x30`/`0x31` | `0x1B` | Output 1/2 增益（`amixer sset 「Output 1」 33`）|

**开机自动生效路径**（写进 drop-in 了，不用手工再敲）：

```
zynq-audio.service
  ExecStartPre ① audio_cap_init.py   → i2cset -f -y 1 0x10 0x0A 0x00  (强制写，绕开驱动占用)
  ExecStartPre ② amixer Playback 192 / Output 1 33 / Output 2 33
  ExecStartPre ③ i2cget 0x1D → (v & 0xfc) | 1 → i2cset 0x1D   (Vpp_scale=1)
  ExecStart /home/zynq/ui/audio_alsa_svc.py   ★ 被 alsa.conf drop-in 覆盖
```

**新板子必须做的**：

1. 确认 `aplay -l` 能看到 `card 0: xlnxi2ssndcard0`（没看到 = dtb 里 es8388 节点没生效，检查 §7.1 的 `system.dtb`）；
2. 确认 `lsmod | grep es8388` 有 `snd_soc_es8388`；
3. 装好 `/etc/asound.conf`；
4. 跑一次 `sudo python3 /home/zynq/audio_cap_init.py`（部署脚本会自动做）；
5. 录一段验证：`sudo python3 /home/zynq/audio_verify.py` 或 `board_audio_state.py`。

`audio_cap_init.py` 与 `audio_verify.py` 的 idempotent 性：前者是**幂等**的（无条件把 0x0A 写成 0x00），重复跑无害。

### 7.4 内核模块 `.ko`（仅在需要时替换）

板子上放了两个**自编译**的 ES8388 驱动模块：

| 文件 | 字节 | 说明 |
|---|---|---|
| `/home/zynq/snd-soc-es8388.ko` | 30400 | 修改版驱动（改了 ADC 输入默认值）|
| `/home/zynq/snd-soc-es8388-fixed.ko` | 30876 | 进一步修复版 |

**当前系统实际加载的不是它们**（`lsmod` 显示的是内核自带的 `snd_soc_es8388`，24576 字节），

这两个 `.ko` 作为**备选方案**带着即可，正常部署不需要 `insmod`。

### 7.5 设备树改动（务必备份原版）

`/mnt/boot/system.dtb`（29180 字节，md5 `ece3cd8d656c7b26cd39ee8c8585d001`）已被改过，
和原版（`system.dtb.bak_es8388_20260928`，29177 字节）不同。改动至少包括：

**以 `/mnt/boot/system.dtb` 为准**，其余作为参考。换板子时如果 dtb 不对，PL 寄存器读出来就是 SIGBUS。

## 11. 复现本清单的原始命令

全部通过 `D:\ubuntu_iso\board.py`（paramiko SSH 封装）在板子上执行。

```bash
# ① 枚举 + md5 + 字节数
find /home/zynq/ui -maxdepth 1 -type f ! -path '*/__pycache__/*' -printf '%p\n'
find /home/zynq/agent -maxdepth 2 -type f ! -path '*/__pycache__/*' -printf '%p\n'
find /home/zynq -maxdepth 1 -type f -printf '%p\n'
while read -r p; do sudo -n md5sum "$p"; sudo -n stat -c %s "$p"; done

# ② 服务真实启动参数
systemctl cat zynq-desktop zynq-agent zynq-audio cloud-api thermal-guard zynq-screen-guard
systemctl show <每个服务> -p ExecStart -p ExecStartPre -p EnvironmentFiles -p User

# ③ 依赖闭包（AST 解析 import + importlib/__import__ 动态加载）
python3 /tmp/_ba_imports2.py

# ④ 硬件侧
ls -l /mnt/boot/ ; mount | grep boot
sudo python3 /home/zynq/dump_es8388_regs.py   # 或 i2cget -y 1 0x10 <reg>
aplay -l ; lsmod | grep -i es8388

# ⑤ /etc 配置（脱敏后读出）
sudo cat /etc/zynq-baidu.env /etc/zynq-baidu-ocr.env /etc/zynq-agent.env /etc/xiaobai-cloud.json
```

> 提示：`board.py -f` 固定把脚本上传到 `/tmp/_s.sh`。如果**多人同时**用同一个 `board.py`，
> 会互相覆盖（本次审计就遇到过脚本被截断）。建议改用 `python board.py -p 本地脚本 /tmp/唯一名.sh`
> 再 `python board.py "bash /tmp/唯一名.sh"`。另外可设 `BOARD_IP=<ip>` 跳过自动扫描。
